Deep inspection

Analysis

The product is two programs sharing one data file. The editor writes show.json; the show reads it. Everything else (ingest, presenter, backups) exists to make those two reliable on one specific laptop, on one specific evening, with content that does not exist yet.

System shape

Why this shape

One laptop does everything. You confirmed the projector is this laptop. That removes the network entirely: the server binds to localhost, the browser is Chrome on the same machine, and the TV is just a second display over HDMI (or the laptop screen itself). There is no deployment step; npm run show is the whole runbook.

The show never touches an original file. Every photo is re-encoded to WebP at 2560 px, every video to H.264 1080p with normalized loudness. This is what makes playback predictable: no HEIC decoding at show time, no WhatsApp codec surprises, no 40 MB camera JPEGs decoding on a slide change.

Derived data is disposable, edited data is sacred. The cache can be deleted and rebuilt. show.json is written atomically with a timestamped backup on every save and referenced by content hash, so renaming or moving a photo in media/ never breaks a slide.

The editor and the show share one renderer. The preview pane in the editor is the same slide component the show uses. What you see while editing is what the family sees, including typography and safe margins.

Data model

One Show object: metadata, settings, music tracks, and chapters that contain slides. Slides reference assets by content-hash id. Twelve slide types, each with a small set of props; the editor's inspector is generated from the type's schema. Chapters carry defaults (duration, transition, Ken Burns preset) and a music binding (track, start offset, fade). The server validates with zod on every write and refuses a save that would corrupt the file.

Playback engine

A scheduler owns a queue of slides. For each slide it builds one GSAP timeline (enter, hold, exit), preloads the next three slides' images with createImageBitmap, and the next video with preload=auto. Transitions run between two stacked layers, so the outgoing slide keeps animating while the incoming one enters. Audio is one Web Audio graph; ducking is a gain tween triggered by the scheduler when a video slide enters and released 1.2 s after it ends. Keyboard events map to clicker keys (PageUp/PageDown) so any presenter remote works.

Ingest pipeline

Content-hash → derive → index. Idempotent and incremental: re-running on 2,000 processed photos costs seconds. Worker pool sized to cores minus one. Progress streams to the editor over SSE so the library fills in while you keep working. A watcher picks up new drops in development.

Risks, scored

HIGH
HEIC photos fail to decode. Fallback chain (sharp → heic-convert → ffmpeg). Tested the moment the first iPhone photo lands. Last resort: export JPEG from Photos on the phone.
HIGH
Hardware surprise on the night (HDMI audio, scaling, sleep). Mitigated by rehearsal on the exact laptop on Thursday, Focus Assist, power plan, and the backup MP4 in VLC.
MED
WhatsApp videos with odd codecs or rotation flags. Every clip is re-encoded; the show never plays an original.
MED
Thousands of photos make the editor sluggish. Virtualized grid, 400 px thumbs, server-side filters, blur placeholders.
MED
Hebrew letter animation breaks (SplitText RTL). Day-1 spike; fallback to word-level reveal, which this prototype already uses.
LOW
Music ends before a chapter does. Editor warning (see the storyboard) plus automatic seamless loop with a 2 s crossfade.
LOW
Scope creep. Engine and editor first; visual extras are a ranked list on Wednesday; anything unfinished by Wednesday evening is cut.

What the prototype proves and what it does not

Proven here

  • Editor information architecture and RTL layout
  • Slide types, typography, motion curves, transitions
  • Editor → show → presenter data flow
  • Ducking behavior and clicker key mapping
  • Focal point, duration, transition, advance mode editing

Only in the real build

  • Real photos (placeholders are generated here)
  • Real video playback and ffmpeg normalization
  • File persistence with backups (here: browser storage)
  • Virtualized library for thousands of items
  • Second-display presenter over BroadcastChannel
